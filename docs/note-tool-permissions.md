# 笔记工具的读写规则

确认单位是用户本次对同一份笔记提出的完整修改要求，不是一个段落或章节。先读取所需原文，汇总全部修改，展示一份前后对照预览，再请求一次确认，确认后整体保存。

- 多章节优化、合并和删除使用 `knowledge_note_update(operation: "batch_edit", edits: [{oldText, newText}, ...])`。最多 100 处修改，全部原文锚点基于同一个 `expectedVersion`，必须唯一且互不重叠；任何一处不合法则整批拒绝，不做部分写入。范围外内容逐字符保留，成功只生成一个新版本。
- 单处修改仍可使用 `replace_range`；用户明确要求整篇重构时使用 `replace_content`，不要求逐章申请确认。真正新增材料才使用 `append_content`。
- 服务端生成章节名称、原文行号、修改前和修改后的具体内容，不依赖模型仅提供一句泛化摘要。`summary` 可额外说明本次修改目的。
- 初次提案返回最多 12000 字符预览、完整修改位置列表和 `nextPreviewOffset`。超过长度时明确标注未展示完，必须调用 `knowledge_note_preview(confirmationId, offset)` 连续读取剩余部分，再向用户展示或清楚标注的摘要对照；不能只问“是否确认”。该只读工具属于所有会话的知识工具，不是伙伴专属。
- 未读完预览不能保存；若提前取得同意，则必须补全展示并等待新的下一轮确认，不能在补读后沿用旧同意直接写入。空白变化或无变化不生成确认提案。

- 列目录、搜索、读取笔记不要求当前消息出现“笔记”或提供额外语义授权，也不要求笔记被知识库挂载或引用。
- 会话签名句柄、存储连接鉴权和内容类型校验保留；这不公开匿名 HTTP 访问，也不改变知识库的挂载权限。
- 创建、更新、改名和移动先产生待确认方案，返回具体目标、去向及内容预览，不实际写入。助手应总结方案并结束本轮，等待用户回复。
- 下一轮用户回复“确认”“可以”“好的”“按这个改”等简短同意后，调用 `knowledge_note_confirm` 执行服务端保存的原方案。不得重新生成或替换内容。拒绝或改变要求会取消旧方案；每个会话只保留一个方案，15 分钟过期，重启失效，成功或失败后均不可重复确认。
- 已挂载知识文档的引用不再豁免笔记更新授权。内容写入仍要求先读版本，过期版本拒绝覆盖。
- `replace_content` 明确标注整篇覆盖，前后预览仅省略首尾完全相同的行；原文超过 200000 字符时应使用 `batch_edit`，避免生成无界的全文覆盖预览。不通过“确认全文覆盖”等特定文字取权。
- 删除保持原有明确删除指令及引用保护，不扩大到知识库文档的泛化表达。
- 不调用 DSH 弹窗审批，不依赖其 `ask/never` 策略。确认只接受当前用户的直接消息，不接受工具结果或模型自行确认。

以上规则针对通用笔记工具，不改变伙伴心跳等独立、显式配置的记录流程。
